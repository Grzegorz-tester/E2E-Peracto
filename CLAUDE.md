# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-project E2E automation framework (Playwright + Cucumber + TypeScript) that runs the
same generic Gherkin step library against ~20 different Shopify/Peracto storefronts (KOOL,
Watco and its regional variants, Insinkerator, HIB, Indespension, Andy Thornton, MIPA,
Russells, JTDove, Carbon Admin, ...). Each project supplies its own config and feature files;
almost no project-specific TypeScript should be needed.

This is a regression suite for Peracto/Shopify projects. **Never create real orders for the HIB
project.** For every project, mark checkout test data as a Velstar test (in the notes field, or
as the customer's name/surname: "Velstar Test").

## Commands

Tests are run per-project via `COMMON_CONFIG_FILE`, which points at that project's `env/<Project>.env`:

```bash
COMMON_CONFIG_FILE=env/KOOL.env ./run_tests.sh regression
```

Cucumber profiles (`dev`, `smoke`, `regression`, plus a few project-specific ones like
`MIPA_regression`) are defined in `src/index.ts`, transpiled into `dist/index.js`, and picked
up via the root `cucumber.js` (`module.exports = require('./dist')`). **Editing a profile or any
step definition requires a recompile** - `yarn cucumber` (= `cucumber-compile`) always runs
`transpile` first; running `cucumber-js` directly against stale `dist/` will not pick up source
changes.

**Report generation is NOT automatic on a failing run unless you use `run_tests.sh` or one of the
named `yarn dev`/`yarn smoke`/`yarn regression` scripts.** `postcucumber` (the HTML/PDF report
step) is wired as yarn's implicit post-hook for a script literally named `cucumber` - so running
`yarn cucumber-compile` directly never triggers it (wrong script name, confirmed: tests run,
`reports/report.json` is written, but no HTML/PDF). More importantly, **even `yarn cucumber
--profile X` only auto-runs the hook when every scenario passes** - yarn only fires a post-hook
after its script exits 0, so a single failed/undefined step makes the whole command exit 1 and
the report step never runs (confirmed live: a deliberately-failing scenario produced
`report.json` but no `cucumber-html-report.html`/`cucumber-pdf-report.pdf`). `run_tests.sh` and
the named `yarn dev`/`smoke`/`regression` scripts both work around this deliberately - they
capture the real exit code, always run `yarn postcucumber` regardless of it, then re-exit with
that original code - so report generation never depends on the run having passed. Prefer
`run_tests.sh <tag>` over calling `cucumber` directly for exactly this reason, especially for any
run where a failure is plausible (i.e. most runs against real projects, as opposed to a
`--dry-run`, which always exits 0 and can mask this).

```bash
yarn cucumber              # transpile src -> dist, then run cucumber-js (report only on 100% pass)
yarn dev                   # --profile dev (@dev tag), report generated regardless of outcome
yarn smoke                 # --profile smoke (@smoke tag), report generated regardless of outcome
yarn regression            # --profile regression (@regression tag), report generated regardless of outcome
yarn test                  # cucumber + HTML/PDF report generation
yarn clean                 # rimraf dist reports
```

Run a single feature file or scenario by narrowing `FEATURE_PATH` (set per-project in
`env/<Project>.env`) or by tagging the scenario and filtering with `--tags`:

```bash
COMMON_CONFIG_FILE=env/KOOL.env FEATURE_PATH=src/features/KOOL_features/basket.feature ./run_tests.sh regression
```

(Appending the feature path as a bare CLI argument instead does **not** narrow the run - cucumber-js
concatenates it with the profile's own `FEATURE_PATH` glob rather than replacing it, so every other
matching feature still runs too.)

Reports (HTML + PDF) are generated by `postcucumber`
(`src/reporter/cucumber-report.ts`, `src/reporter/pdf-report.ts`) from `reports/report.json`,
and always run even if the cucumber run itself fails (`run_tests.sh` preserves the exit code;
`yarn dev`/`smoke`/`regression` use `||` for the same reason).

No lint/typecheck script is defined in `package.json`; TypeScript errors surface at transpile
time (`babel --extensions .ts`, which strips types rather than checking them - Babel will
silently pass code `tsc` would reject).

## Architecture

**Everything is data-driven per project.** A project = one `env/<Project>.env` file + one
`config/<Project>_config/` directory. There is no per-project TypeScript; behaviour is entirely
generic step definitions parameterized by config.

- `env/<Project>.env` - points at that project's config paths (`HOSTS_URL_PATH`,
  `PAGES_URL_PATH`, `PAGE_ELEMENTS_PATH`, `USERS_CONFIG_PATH`), its `LOGIN_URL`/`LOGIN_SUCCESS_URL`,
  a `PROJECT` slug (used for env-var credential overrides), and `FEATURE_PATH` (scopes a run to
  that project's own `src/features/<Project>_features/` folder so shared tags like `@smoke`
  don't pull in every other project's scenarios).
- `config/<Project>_config/hosts.json` - environment name (e.g. `staging`) -> base URL.
- `config/<Project>_config/pages.json` - page ID -> `{ route, regex }`. The `regex` is how the
  framework identifies "what page am I on" from the current URL path
  (`getCurrentPageId` / `pathMatchesPageId` in `src/step-definitions/support-functions/navigation-behaviour.ts`).
- `config/<Project>_config/mappings/*.json` - one file per page ID (filename = page ID, e.g.
  `basket.json`, `checkout.json`), each an element-key -> CSS/text selector map, plus a
  `common.json` used as a fallback when a key isn't found on the current page
  (`getElementLocator` in `src/step-definitions/support-functions/web-element-helper.ts`).
- `config/<Project>_config/users.json` - defines which user types exist (e.g. `"logged in"`,
  `"guest"`) with blank credentials; real credentials come from environment variables at runtime
  (see `.env.example`), never committed. `loadGlobalConfig` (`src/env/loadGlobalConfig.ts`)
  resolves `<PROJECT>_<USER_TYPE>_EMAIL`/`_PASSWORD` first, falling back to the generic
  `<USER_TYPE>_EMAIL`/`_PASSWORD`, since each storefront's real test account is usually a
  distinct (often plus-aliased) address rather than one shared identity.

**Config loading flow:** `src/index.ts` loads `env/common.env` then `.env` (gitignored, real
creds) via dotenv at cucumber-profile-build time. Per-scenario, `ScenarioWorld`
(`src/step-definitions/setup/world.ts`) calls `loadGlobalConfig()` to read the project's
hosts/pages/mappings/users JSON (based on the env vars set above) into a single `GlobalConfig`
object attached to `this.globalConfig`, and opens a fresh Playwright browser/context/page per
scenario in `Before`/`After` hooks (`src/step-definitions/setup/hooks.ts`), recording video and
capturing a screenshot on failure. The full JSON is deliberately *not* passed through cucumber's
`--world-parameters`: cucumber re-tokenizes that whole profile string with `string-argv`, which
mis-splits selector values containing an escaped quote followed by a space (e.g.
`:text-is(\"Reset Password\")`).

**Step definitions are split into three layers:**
- `src/step-definitions/base-steps/interactions/*.ts` - generic Given/When steps (click, fill,
  check, navigate, basket, checkout, PDP carousel/accordion/comparison-table, PLP filter/sort,
  quote builder, product configurator/registration, search drawer, address book, currency,
  footer, newsletter popup...). Every step resolves selectors through
  `getElementLocator(page, elementKey, globalConfig)` - never a hardcoded selector.
- `src/step-definitions/base-steps/assertions/*.ts` - generic Then steps (visibility, value,
  checked state, attribute, HTML5 validity, current page).
- `src/step-definitions/base-steps/users/user.ts` - the compound login step
  (`I am navigating the page as a "X" user`), which reads `login.json`'s mapping plus
  `LOGIN_SUCCESS_URL` to log in as any user type for any project.
- `src/step-definitions/support-functions/*.ts` - the actual Playwright mechanics
  (`html-behaviour.ts` clickElement/clickElementAtIndex, `wait-for-behaviour.ts`, page-ID
  resolution, payment test card data) that the step layers above call into.

**Feature files** live under `src/features/<Project>_features/` (or nested subfolders for larger
admin suites, e.g. `Carbon_admin/Configuration`, `Carbon_admin/Products`). Prefer the existing
generic steps over writing new ones - most interactions are already covered: `I click on the "X"
button/link/element`, `I fill in the "X" input field with "Y"`, `I check the "X"`, assertion
steps, and the ordinal `I click on the "1st" "X" element` for positional clicks. Two escape
hatches exist for common special cases and are reusable by any project:
- `I click on the "X" button/link/element if present` - an element that only sometimes appears
  (a modal, an interstitial).
- `I check the "X", retrying until it is checked` - a checkbox that doesn't reliably register as
  checked on the first click.

Only add a new bespoke step when the action genuinely can't be expressed with the above (e.g.
stashing a dynamic value for later reuse in the same scenario, a multi-step retry loop like
address autocomplete, or reaching into an iframe via `frameLocator`). Make it reusable by other
projects, not just the one being built for it: resolve elements through `getElementLocator`
(the selector belongs in that project's `config/<Project>_config/mappings/*.json`, not in
TypeScript) and parametrize whatever varies as step arguments.

## Setting up a new project

Adding a new project means creating its skeleton, not writing new TypeScript:

- `env/<Project>.env` (and `env/<Project>_<Region>.env` per regional variant, as Watco does).
- `config/<Project>_config/{hosts.json,pages.json,users.json,mappings/*.json}`.
- `src/features/<Project>_features/*.feature`.

A storefront and its admin site (e.g. Carbon Admin alongside its storefront) are set up as
**separate projects**, each with its own `env/*.env` and `config/*_config/` - the admin site is
not just another page mapping bolted onto the storefront project.

`hosts.json` typically defines both a `staging` and a production/live host entry; which one a
run targets is controlled by `UI_AUTOMATION_HOST` in the project's `env/*.env`.

### Staging vs production rules

Both environments have a storefront site and an admin site.

- **Staging**: free rein. Place real orders, and freely create/read/update/delete data on both
  the storefront and the admin site.
- **Production/live**: **never place a real order** on the storefront. Editing the test user's
  own account (profile details, address book, etc.) is fine. The admin site on production is
  **read-only** - no creating, editing, or deleting anything through the admin site; only editing
  the test user's own storefront-side account data is permitted, and only on the storefront.

When writing or tagging a scenario, be clear about which environment and site it's meant for -
don't assume a step that's safe on staging (placing an order, editing admin content) is safe to
run against production just because the same feature file's `FEATURE_PATH`/tag also matches a
production run.

### Peracto Admin: shared boilerplate across tenants

KOOL, Indespension and Carbon Admin (and any future Peracto-admin tenant) all run the same
underlying Peracto Admin product - confirmed live across multiple tenants: identical
data-testid selectors, routes, nav structure and error copy. Rather than maintaining a
near-identical copy of the same admin feature files per project, the shared scenarios (login,
every tab has real content or a genuine empty state, clicking a tab's first item redirects to
its own detail page) live once in `src/features/Carbon_admin/`, since Carbon Admin is the
boilerplate project most Peracto admin projects are set up from. Each tenant's own
`env/<Project>_ADMIN.env` points its `FEATURE_PATH` at that same shared folder
(`./src/features/Carbon_admin/**/*.feature`) rather than copying the files - only the host URL,
credentials and `config/<Project>_ADMIN_config/` mapping/route specifics differ per project,
never the scenarios themselves.

Because the shared scenarios assume a "typical" Peracto Admin tab set, a new tenant won't
always fit exactly:

- **A tenant is missing a tab that the shared suite expects** (e.g. no Orders, no Products):
  don't force that tenant to somehow pass the shared Scenario Outline's row for a tab it
  doesn't have. Remove that tab's row from the relevant Examples table in that tenant's own
  copy of the reasoning - but since the feature files are shared, not copied, this means either
  (a) confirming the nav item that maps to it is genuinely absent for every tenant using this
  folder, or (b) if only some tenants lack it, that tab no longer belongs in the shared
  boilerplate's Examples table and needs a per-tenant mechanism instead (e.g. tagging that row
  and excluding the tag for tenants that lack it) rather than silently breaking for that one
  project.
- **A tenant has its own bespoke tab that the others don't** (e.g. a "Test Harness" section):
  don't add it to the shared `Carbon_admin` feature files - that would run a tab that doesn't
  exist against every other tenant. Give that tenant its own small project-specific feature file
  alongside the shared ones (e.g. `src/features/<Project>_features/admin-extras.feature`, or a
  file within its own `<Project>_ADMIN` feature path added in addition to the shared
  `FEATURE_PATH` glob) covering just its bespoke tab, following the same generic step /
  `getElementLocator` conventions as everywhere else.
- Before assuming a shared-suite failure is a tab genuinely missing from a tenant, verify it
  live first (nav item absent vs. selector/config gap) - the same rigor used to confirm every
  other quirk in this document, so a real config mistake doesn't get waved off as "this tenant
  doesn't have that".

## Known quirks worth knowing before debugging a failure

- Browser permissions (geolocation, etc.) are explicitly denied in `ScenarioWorld.init` rather
  than left unset, because an undecided permission auto-denies invisibly in headless mode but
  blocks indefinitely in headed mode waiting for a native prompt.
- Navigation uses `waitUntil: "domcontentloaded"`, not Playwright's default `"load"` - `"load"`
  has been observed hanging past 60s on flaky third-party embeds (newsletter popups, reCAPTCHA,
  analytics) even once the page itself is fully usable.
- `force: true` on clicks skips only Playwright's "receives events"/"stable" checks (the element
  still must be attached and visible); it clicks at the target's bounding-box center, which
  breaks on oversized wrapper elements (a `<label>` wrapping a multi-line paragraph) - use the
  "precisely" (non-forced) click variant for those instead.
- Cookie/preference-centre overlays can reappear after being dismissed once. The
  `..., dismissing the "X" if it interferes` click steps re-check and re-dismiss before every
  retry attempt, not just the first.
- HIB's staging site has known intermittent flakiness - don't over-invest chasing it.
